CASE 02 // APPLIED AI

Text-to-SQL:
making LLMs trustworthy.

A controlled graph workflow for translating business questions into Snowflake SQL, with two-stage retrieval, explicit validation, bounded retries, and human review.

The problem

A data team supporting senior business stakeholders needed help producing complex Snowflake queries for portfolio and project performance reviews. The information was spread across multiple tables maintained by different teams, and manual query writing could take days.

The architectural decision

I proposed a graph-based workflow rather than multi-agent orchestration. The core process was sequential: understand the question, retrieve context, generate SQL, validate, then either execute through a controlled path or return SQL for review. A graph made execution order explicit, easier to debug, and predictable without adding unnecessary coordination complexity.

How the workflow works

01 / Retrieve business meaning and schema

The workflow retrieves semantic information—table descriptions, metrics, and business relationships—from S3. It extracts entities such as metrics, filters, and grouping from the question, then retrieves relevant DDL through a Bedrock Knowledge Base. This separates what the user means from how the data is physically represented.

02 / Generate and validate

A ReAct agent generates SQL using the retrieved context. SQLGlot parses the query and checks that it is SELECT-only. If validation fails, the error is fed back for regeneration, with retries bounded to three attempts.

03 / Keep a human in the loop

A routing function determines whether to return SQL for manual review, proceed through the controlled execution path, retry when attempts remain, or return an error. The human review gate is part of the workflow, not an afterthought.

Failure analysis: schema drift

During integration testing, upstream table changes left the semantic layer with stale column names and table structures. The model generated plausible SQL against incorrect context, so retries could not fix the root cause. We corrected the semantic layer and added a freshness mechanism using Snowflake triggers to update a schema URL, which the workflow reads at query time.

Outcome and limits

The data team is using the solution in a pilot as a starting point for query generation, with generated SQL either run through the approved path or modified manually. A production-wide adoption metric was not available at the time of this project, so this portfolio does not claim one.

When retries fail consistently, inspect the inputs and system boundaries before blaming the model.

Design principles

  • Prefer deterministic orchestration when the process is fundamentally sequential.
  • Separate retrieval, generation, validation, and execution concerns.
  • Bound retries and make failure states explicit.
  • Use defense in depth: SQL validation, read-only credentials, and human review.
  • Treat schema freshness as a data integration problem, not a prompt problem.
